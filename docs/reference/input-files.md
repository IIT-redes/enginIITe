# Input files

A case reads everything from `data_in/<net_folder>/`, where `net_folder` is set in the [configuration file](configuration.md). The script `scripts/validate_inputs.py` checks every rule on this page (see [Check inputs](../howto/check-your-inputs.md)).

```
data_in/
└── <net_folder>/
    ├── network/      the network workbook
    ├── profile/      time series of loads, generation and storage
    └── fsp_files/    tables of flexibility service providers
```

The three sub-folders must exist. The platform also creates `market_inputs/` next to them for the files it generates.

## Network workbook

One `.xlsx` file in `network/`, read with the pandapower Excel format. Besides the usual pandapower sheets (`bus`, `line`, `load`, `sgen`, `ext_grid`, ...), these rules apply.

- The network needs an external grid, which acts as the slack.
- Lines and transformers share one set of column names in the sensitivity tables, so **every line and transformer name must be unique** across all branch types.
- Loads, static generators and batteries should have names, because FSPs are matched to them by name.
- Each table that has profiles (`load`, `sgen`, `storage`) needs the three columns `denorm_profile`, `norm_profile` and `internal_profile`, empty where not used.
- If the case has battery FSPs, the `storage` table needs `soc_percent`, `min_e_mwh`, `max_e_mwh` and `sn_mva`.

### Profile column

Fill exactly one of the three columns for each element that should vary in time. An element with none stays constant.

| Column | Meaning | Profile file |
|---|---|---|
| `denorm_profile` | The element follows an absolute profile. | A column per element index, in MW or MVAr. |
| `norm_profile` | The element follows a per-unit curve scaled by its own `p_mw` or `q_mvar`. The cell holds the name of the curve. | A column named like the curve. |
| `internal_profile` | The profile is generated by a module. | A parameter file read by that module. |

## Profile files

Files in `profile/`, named in `network.profile` of the configuration. Both `.xlsx` and `.csv` are accepted.

- The rows are time steps and they are cut **by position**, so row 0 is the first hour. The file needs at least as many rows as the end of `simulation_window`, and cells inside the window cannot be empty.
- For an `.xlsx` file, the first sheet must have the same name as the file without the extension.
- Denormalised profiles have integer column names, which are the element indices of the network table. Every element that uses the file needs a column.
- Normalised profiles have one column per curve name used in the `norm_profile` column. There are separate files for active power (`p`) and reactive power (`q`).
- All values must be numeric, so keep headers and notes out of the data area.

The profile of each element is multiplied by the scenario factor of its category (`scen_factor_load` and so on).

### Supply voltage profile

The optional key `network.ext_grid_profile` names a file in `profile/` with the voltage set-point of the external grid, which is the upstream supply, for every time step. It lets each time step or snapshot have its own supply voltage, so that a scenario with a high or a low upstream voltage is simulated as such. The voltage applies to the power flow before the market, to the sensitivity tables of that time step and to every verification after the market.

- The file has the layout of the other profile files, with one row per time step and the sheet named like the file when it is an `.xlsx`.
- It has one column per `ext_grid` of the network, named with its integer index. A column that is not an `ext_grid` index stops the run.
- The values are absolute voltages in per unit, not multipliers, and they must be between 0.8 and 1.2.
- Without the key, the set-point of the network file is used at every time step.

## FSP tables

One file per product in `fsp_files/`, named under `network.fsp.fsp_input_filename`. They are `.xlsx` files with the table in the sheet `fsp_sheetname`, or `.csv` files. **The header is on the second row** of the sheet, so the first row is free for a title or a note.

Every product file must contain exactly the same set of FSP types. The product (`P`, `Q` or `PQ`) is expressed through the shares, not through a separate switch. For example, a `P` file normally has zero reactive shares.

### Columns

| Column | Meaning |
|---|---|
| `id` | Identifier of the FSP. |
| `name` | Name of the FSP. It must equal the `name` of an element in the network and be unique within its type. |
| `type` | `A` flexible load, `B` generator, `C` battery. |
| `bus` | Bus of the element. Together with `name` it must match **exactly one** element. |
| `mva` | Rating in MVA, scaled by the scenario factor of the category. |
| `mw`, `mvar` | Declared active and reactive power of the element. The table must have both columns. |
| `Pup`, `Pdown` | Share of the reference power that can be changed upward or downward in active power. |
| `Qup`, `Qdown` | The same in reactive power. |
| `Pup_cost`, `Pdown_cost` | Price of an upward or downward active power activation. |
| `Qup_cost`, `Qdown_cost` | Price of an upward or downward reactive power activation. |
| `bidding_strategy` | What the shares multiply. `initial_value` uses the baseline power of each hour. `mva_value` uses the rating `mva`. `headroom_value` uses the room between the operating point and the technical limit of the element. |
| `aggregator_name` | Leave empty. The aggregator model is not connected end to end. |

The shares are multiplied by the bid coefficient `k` of the scenario tag `F0k`. Shares cannot be negative, and negative prices raise a warning.

### Element controlled by an FSP

| Type | Network table | Notes |
|---|---|---|
| `A` | `load` | Fixed power factor. The reactive bounds follow the active ones. |
| `B` | `sgen` | The reactive range depends on the rating. |
| `C` | `storage` | State of charge is limited only when `intertemp_cons` is `true`. |

## Generated files

Under `market_inputs/` the platform writes the sensitivity tables, the hours to study, the detected needs and one workbook per FSP type and scenario. Do not edit them by hand. If a case changes, delete them or set `force_HVM` and `force_HCM` to `true` (see [Configuration](configuration.md)). The results are described in [Output files](output-files.md).
