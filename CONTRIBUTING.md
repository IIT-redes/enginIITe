# Contributing

This page covers setup, how to check a change before proposing it, and what a good contribution looks like.

## Set up

Create the environment and activate it. The environment targets Python 3.9 and pins `gurobipy` to 11.0.1, the version of the reference results. Gurobi 12 also works.

```bash
conda env create -f environment.yml
conda activate enginiite
```

Running a simulation needs a Gurobi licence. Most of the checks below do not.

## Check a change

Run everything from the root of the repository, the folder that contains `pyproject.toml`.

| What | Command | Needs a solver licence |
|---|---|---|
| Unit tests | `python -m unittest discover -s tests/unit` | No |
| Regression of the examples | `python -m unittest discover -s tests/regression` | Only to run an example that has no finished run |
| Inputs of a case | `python scripts/validate_inputs.py <config.yaml> --root <workspace>` | No |

All tests must pass before a change is proposed. If you fix a defect, add a test that fails without the fix. Some tests document behaviour that is known to be wrong and are marked as such, so when a fix makes one of them pass, remove the marker in the same change.

## Change guidelines

- **Small and focused.** One idea per change, so that it can be reviewed in one sitting.
- **Tested.** New behaviour comes with tests, and a changed behaviour comes with an updated test.
- **Documented.** If a parameter, an input format or an output changes, update the matching page in [`docs/reference/`](docs/reference/). The configuration, the input files and the validator codes each have a page, and the validator and its documentation are kept in step by tests.
- **Conservative with files.** Avoid renaming or moving files and avoid mass reformatting in a change that does something else. They make the history hard to follow and cause conflicts for everyone.

## Data

The repository must not contain data that you do not have the right to publish. Input data of real networks, prices or profiles stay out unless their owner has agreed in writing. For examples and tests, prefer small synthetic cases.

Do not commit results (`data_out/`) or files generated by the platform (`market_inputs/`, `*.lp`).

## Commit messages

Use [conventional commits](https://www.conventionalcommits.org/) in English, with a short subject in the imperative.

```
feat: add a check for empty profile cells
fix: close the workbook after reading a profile
docs: describe the output workbooks
test: cover the hours selection for voltage problems
```

Explain the reason for the change in the body when it is not obvious from the subject.

## Reporting a problem

Open an issue and choose the matching template. A good report contains the configuration file (without private data), the exact command, the full error message and the versions of Python, pandapower and Gurobi. If the problem is in your inputs, run the validator first and attach its output.

## Proposing a change

Open a pull request and fill in the template. Describe what changes and why, mention the tests you ran, and link the issue if there is one. Reviewers may ask for changes. Keep the discussion focused on the code.
